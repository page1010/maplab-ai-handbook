# task-progress-guide.md — 任務紀錄與接續技能書（必拿）

**這是所有 Agent、所有任務都必須讀的技能書。不可跳過。**

> 核心目的：讓每個 Agent 養成「做一步記一步」的習慣，確保 session 斷線時進度不丟、接手者不迷路、Owner 隨時知道你在幹嘛。

---

## 1. 為什麼這本是必拿

系統反覆出現的問題：
- Agent 一口氣衝到底，中間出錯不回報，最後才發現方向錯
- Session 斷線後新 Agent 接手，不知道上一個做到哪，從頭讀起浪費時間
- Agent 選了做法 A 但行不通，自己默默換成 B，Owner 不知道
- 大任務沒拆分，做到一半 context 爆掉，前面的進度全部丟失

這本技能書解決以上所有問題。

---

## 2. 每步紀錄（Progress Log）

**時機**：每完成一個可獨立描述的步驟，立即紀錄。不是做完全部才寫。

**格式**：

```
Progress Log #[序號]
- Done: [用一句話描述剛完成什麼]
- Result: [成功 / 失敗 / 部分完成 — 附具體證據]
- Next: [下一步要做什麼]
- Blocker: [卡住什麼，沒有就寫「無」]
```

**範例**：

```
Progress Log #3
- Done: 從 TimeTree IndexedDB 提取事件資料
- Result: 成功，746 筆外燴事件，392 個日期
- Next: 將 JSON 寫入 GitHub data/ 資料夾
- Blocker: 跨 origin 無法直接傳資料，需找替代方案
```

**原則**：
- Result 欄位要有證據，不能只寫「完成了」。數字、檔名、commit hash 都算
- 如果 Result 是失敗，必須寫為什麼失敗，不能只寫「沒成功」
- Blocker 不是恥辱，是資訊。寫出來才能解決

---

## 3. 子任務切割

**時機**：任務預估超過 5 個步驟時，開始前先拆。

**方法**：

1. 列出所有需要做的事（不管順序）
2. 分組：哪些可以獨立完成、哪些有前後依賴
3. 排序：依賴鏈決定順序
4. 每個子任務寫完成條件：什麼情況下才算「這個子任務做完了」

**格式**：

```
子任務清單（等 Owner 確認順序）

□ 子任務 1：[名稱]
  完成條件：[具體可驗證的條件]
  預估步驟：[幾步]

□ 子任務 2：[名稱]
  依賴：子任務 1
  完成條件：[具體可驗證的條件]
  預估步驟：[幾步]

□ 子任務 3：[名稱]
  完成條件：[具體可驗證的條件]
  預估步驟：[幾步]
```

**原則**：
- 拆完先給 Owner 看，不要自己決定順序就開始做
- 每個子任務完成後，在清單上打勾並寫 Progress Log
- 如果執行中發現需要新增子任務，補上去並通知 Owner

## 4. 接續 Prompt 生成（Resume Prompt）

**時機**：每完成一個子任務、或感覺 session 快結束時。

**目的**：讓下一個 session（可能是同一個 Agent，也可能是新的）能直接貼這段 prompt 就知道要從哪裡接手。

**格式**：

```
Resume Prompt（貼入新 session 即可接續）
---
角色：[Agent 編號 + 名稱]
任務：[Task ID + 名稱]
已完成：
  - [子任務 1 ✅]
  - [子任務 2 ✅]
  - [子任務 3 ⏳ 進行中]
下一步：[具體要做什麼]
必讀檔案：[新 session 需要先讀的檔案清單]
注意事項：[上個 session 踩的坑、做的決策、Owner 的指示]
---
```

**原則**：
- 必讀檔案要具體到路徑，不要寫「相關文件」
- 注意事項要寫具體決策，不要寫「Owner 有一些指示」
- 這段 prompt 是給沒有任何上下文的新 session 看的，所以要自足

---

## 5. 方向偏移處理

**時機**：執行中發現原本選的做法行不通。

**錯誤做法**：自己默默換方案繼續做。
**正確做法**：停下來，回報 Owner，等指示。

**格式**：

```
方向偏移通知
- 原本做法：[A/B/C + 簡述]
- 遇到的問題：[為什麼行不通，附具體證據]
- 已嘗試：[試了什麼修復，結果如何]
- 可能的替代方案：
  A) [做法] — 優點 / 盲點
  B) [做法] — 優點 / 盲點
- 需要 Owner 決定：[具體問題]
```

**原則**：
- 替代方案一樣要列盲點，不要因為急著解決就隱藏風險
- 「已嘗試」很重要 — 告訴 Owner 你不是一碰壁就放棄，但也不是盲目重試 10 次

---

## 6. 臨時任務的紀錄

不在 TASK_QUEUE 裡的臨時任務，一樣遵守以上所有規則。差別只在收尾時：
- 不需要建 Task Card
- 完成後在 CURRENT_STATUS.md「最新決策」登記
- 如果規模大，建議 Owner 補建 TASK_QUEUE 條目
