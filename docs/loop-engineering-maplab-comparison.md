## 一、四種迴圈定義（文章原意）

| 迴圈類型 | 中文名 | 觸發方式 | 完成判斷 | 適合場景 | 盯緊程度 |
|---------|--------|---------|---------|---------|---------|
| Turn-based | 回合制 | 人工每次下指令 | 人工看結果 | 探索型、每步都需判斷 | 最緊（每步人工） |
| Goal-based | 目標導向 | 指令 + 成功條件 | 評估模型自動判斷 | 有明確指標的任務（Lighthouse 90+、最多 5 次） | 中（設條件後放手） |
| Time-driven | 時間驅動 | 排程自動觸發 | 人設定或自動 | 定期例行任務 | 低（排程後不用盯） |
| Proactive | 主動式 | 事件/條件自動觸發 | 代理自行判斷 | 全自動、永遠在線 | 最低（條件自觸發） |

**核心洞察**：迴圈設計 ≠ 寫 prompt，而是設計「誰來觸發」+ 「誰來判斷完成」。

## 二、MAPLAB 現況對照

### 現有三種迴圈

| MAPLAB 機制 | 對應迴圈類型 | 現況 | 健康度 |
|------------|-----------|------|--------|
| Telegram → Owner 下指令 → A1 執行 | **回合制** | 主力運作中 | ✅ 正常，但依賴 Owner 每次手動觸發 |
| A1/A0 每日巡檢（`patrol.sh` cron） | **時間驅動** | 運作中（每日 UTC 01:00 via GitHub Actions） | ✅ 正常，巡檢是無人盯的時間驅動 |
| Dispatch packet + Hermes + Codex | **目標導向** | 架構存在但 Hermes CLI = null，完全卡住 | ❌ 無法啟動，packet 在佇列永遠未被消費 |
| B3 ads 偵測（`patrol.sh` 07-18 新增） | **主動式（事件驅動）** | 偵測條件：utm_source=meta_b3 / Owner 回報 → 自動每日摘要 | 🟡 條件已定義，等第一個觸發事件驗證 |

### 缺口分析

```
Owner 層（觸發者）
  ↓ 回合制（高負擔）
A0/A1 層（執行者）
  ↓ 目標導向（Hermes = null，❌卡住）
Codex/agy 層（工作者）
  ↓ 主動式（B3 條件設定中）
自動輸出
```

**最大缺口**：目標導向層失能 → 所有非回合制任務都卡在佇列，Owner 被迫用 Telegram 手動追每一件事。

## 三、W-SW-NW 與迴圈類型的對應

| 自主派工分級 | 對應迴圈 | 說明 |
|------------|---------|------|
| **W（完全自主）** | 主動式 Proactive | Agent 自行判斷觸發與完成，不需 Owner 知道 |
| **SW（告知不等待）** | 目標導向 Goal-based | 執行後回報結果，Owner 只看摘要不需實時介入 |
| **NW（需批准）** | 回合制 Turn-based | 每步等 Owner 確認才繼續 |

**AskUserQuestion 禁令的迴圈解讀**：
禁止 AskUserQuestion = 強制 agent 從回合制退出，必須在目標導向或主動式框架內自行解決。這是把「每步都問 Owner」的習慣升級為「先自判再告知」。

## 四、治理升級提案

### 提案 1（已實施）：B3 ads patrol 升級為混合迴圈
- **原狀**：B3 廣告成效只能靠 Owner 手動回報
- **升級**：patrol.sh 新增 B3 偵測區塊，utm_source=meta_b3 → 每日自動摘要
- **迴圈類型**：時間驅動（daily patrol）+ 事件驅動（B3 偵測）混合
- **狀態**：✅ 2026-07-18 已上線

### 提案 2（待執行）：解鎖目標導向層
- **問題根因**：Hermes CLI = null，`dispatch packet` 有人投但沒郵差
- **解法**：`which hermes` 確認是否安裝 → 若無，改用 `claude -p` 直接消費 packet.json
- **執行者**：A1 + Owner（確認 Hermes 安裝路徑）
- **影響**：解鎖後 R02/R06/R08/R09 等目標導向任務可自動執行

### 提案 3（設計中）：IS 規則引擎升級為主動式
- **現況**：IS 規則引擎（`scripts/is_rules_gate.sh`）已上線，但觸發需 A1 手動跑
- **升級方向**：設定 launchd 或 GitHub Actions cron 定時跑 is_rules_gate.sh，異常自動推 Telegram
- **迴圈類型**：從手動回合制 → 時間驅動主動式
- **注意**：需確認 is_rules_gate.sh 四參數（SOP1=10%/SOP2=15%/槓桿=1.5x/日跌幅=-3%）穩定後再自動化

### 提案 4（現有機制最佳化）：回合制任務分類
- **問題**：所有 Telegram 任務都走回合制，包括本可自動的例行任務
- **解法**：Owner 發來的任務，A0 先判斷迴圈類型再路由：
  - W → 直接執行 + 事後告知
  - SW → 執行 + 完成後回報
  - NW → 先提確認選項 → 等 Owner 回
- **效果**：Owner 的 Telegram 負擔從「每條任務都要追蹤」減為「只看需要決策的」
