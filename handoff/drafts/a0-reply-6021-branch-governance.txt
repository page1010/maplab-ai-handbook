【Fable5 本人・同 session 續接】

結論:是治理問題,而且實查出來比那句話更嚴重。分支多不是病根,**沒有任何角色被指派去做收斂**才是。四個 repo 的實數如下。

一、investment-os

23 條遠端分支。main 最後一次提交停在 7/16,已經 69 天沒動;而真正跑著模擬倉的那條 research/markyang-finance-20260911 更新到 9/21。

兩條互相缺:main 有 302 個 commit 那條沒有,那條有 82 個 main 沒有。**今天要壓縮出貨,兩條都不能用。**

二、handbook(治理總部自己)

47 條遠端分支。每天在寫的那條比 main 多 588 個 commit,main 另有 90 個它沒有。

更難看的是:main 上最近的提交**全部是每日巡邏寫的 all clear**——巡邏在一條沒有人做事的線上宣告一切正常。今天剛建的稱謂表 NAMING_GLOSSARY.md,在 main 上根本不存在。

三、cdo(最急的一個)

根本不在 main,是在 ops/relocate-register-20260803 這條分支上。22 個檔案改了沒提交,另外約 150 個檔案**從來沒進過版控**——包括 hermes 值班表、operations 每日紀錄、codex 交叉稽核 36 份逐字稿。

「凡走過必留下痕跡」這句話在這裡是破的:這些痕跡只活在這台機器的硬碟上,只有一份,硬碟壞了就沒了。連續 49 輪 git pull 失敗也是同一個原因。

四、agent-bus 是反例

只有 main 一條,零分岔。它沒病的原因很實在:多台機器必須在同一條線上交會,不交會當場就對不上。**單線是可行的,已經有活的證據。**

五、建議的制度(照原話那四件事)

1 出貨只認 main:要壓縮給客人的就是 main 上的某個 tag,其他分支一律當未定稿。
2 每條分支一張卡:誰的、做什麼、哪天併回。沒有卡的到期封成 tag——封存不是刪除,那也是痕跡。
3 收斂要有一個人:固定一個整合官角色,每週跑一次,掃全部分支、列重複功能、裁定收成一條,Owner 只看一張表。
4 重複功能先讓機器判:同一個檔案被兩條分支改到,git 自己算得出來,先出清單;真的兩套實作才需要人裁。
5 好的抉擇也入檔:採用哪條、為什麼採用、被否決那條的理由,寫進決策檔並在合併紀錄裡引用。

六、現在最該先做的一件

不是先建制度,是先止血:**cdo 那約 150 個從未進版控的紀錄先入版控**。

理由很單純——其他幾條都還救得回來,commit 都還在;只有這批不是,它現在只有一份。

只是 cdo 是共用 repo,依現行規則這邊不自行 commit,等一句話就做。

另外兩件要一起裁:handbook 那 588 個 commit 要不要現在併回 main(不併的話巡邏的 all clear 會一直是假的);investment-os 認 main 還是認 markyang 那條當主幹(那是 codex 的主場,建議等他額度回來一起定)。

七、認錯

這條線自己就是累犯。handbook 的 588 個 commit 全部長在一條 chore 分支上,一次都沒併回去。

前兩次歸咎的「範圍只開一個資料夾、只開一個分支」是讀取範圍的錯;查到這裡才看清楚,上游是同一個治理缺口——沒有人負責把線收回來。
