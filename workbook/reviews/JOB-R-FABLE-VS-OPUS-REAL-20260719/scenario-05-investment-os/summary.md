# R05 Investment OS 協作架構 — 真模型對比摘要

執行日期：2026-07-19
模型：Fable=claude-sonnet-4-6 | Opus=claude-opus-4-7（claude CLI）

---

## 模型行為差異觀察

| 維度 | Fable (sonnet-4-6) | Opus (opus-4-7) |
|------|-------|------|
| R1 框架設計 | 四層流水線（採集→分析→整合→執行），結構化 artifact 觸發 | 質疑「訊號同向」定義，區分「訊號解讀」vs「時序解讀」 |
| 門控模型 | 設定 IS-Chief 評分 >75 觸發 + Phase 0/1 分期 | 指出「55% 方向勝率在 N=12 時無法區分技能vs運氣」 |
| 閉環學習 | 設計回流比對表（預測 vs 實際），R1-R5 持續細化 | 提出「先驗證模型本身有 alpha，才值得建閉環」 |
| 頻率問題 | R1-R3 未處理月頻/小時頻不一致問題 | R4 提出「頻率分層匯流」框架 |
| R5 核心洞察 | 「命題書需有可證偽性約束，不能讓 Owner 填無法驗證的目標」 | 「先問訊號是否已被市場定價，沒有 alpha 空間的閉環只是空轉」 |

**Fable 第1→5輪進化：** 四層流水線→Phase 0 人工測試→門控閾值（55%+12樣本）→發現自己設的門「自己過不了」（12 個樣本在 Phase 0 期間拿不到），R5 暴露了自己前 4 輪閾值設計的根本矛盾。

**Opus 第1→5輪進化：** 概念框架質疑→頻率分層匯流架構→「訊號是否已被定價」納入 Phase 0 標準，每輪提出一個 Fable 未注意到的前置條件。

## 適合派工

場景 R05（Investment OS）→ **Opus 做前提驗證 (R1-R3) + Fable 做執行架構 (R2-R5)**

- Opus 的「先驗證 alpha 空間存在，再建閉環」是本場景最關鍵的前提驗證
- Fable 的四層流水線 + 評分卡設計是可部署的系統架構
- 關鍵順序：Opus 的 Phase 0 人工測試（驗證模型可行性）必須先於 Fable 的 Phase 1 自動化，否則自動化空轉
