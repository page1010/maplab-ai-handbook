結論：目前最強的是風控，最弱的是世界觀/終局層與右側動能層。系統已經很會「收集、監控、提醒」，但還不夠會把訊號壓成 Owner 需要的判斷語言：事實、推論、缺資料、失效條件、下一步。

**1. 功能檢討意見**

最幫得上決策的是曝險帳本、死亡清單、盤後風控、財經早報 v2。原因是它們有資料新鮮度、風控閘門、if-then、校準覆盤，接近 Owner 要的「今天能不能動、哪裡不能信、下一步是什麼」。

比較幫不上決策的輸出有幾類：

- Dashboard / Telegram bot / 系統真相地圖：偏入口與治理，不等於決策輔助。若沒有把第一屏壓成「可動/不可動/缺什麼證據」，容易變成看起來很完整但 Owner 還是要自己判讀。
- 夜間進度簡報 / 影子教練：有輔助價值，但本地模型推論與遊戲化 XP 不能當判斷依據；應只當「工作狀態」或「品質警示」。
- 市場事件島 / 富途新聞：資料存在，但若沒有獨立報告、來源日期、事實/推論/缺資料/下一步，對 Owner 來說只是 raw input。
- 量化資源橋接：是參考庫，不是決策輸出；除非連到具體 thesis、資料欄位、回測限制與適用條件。
- 模擬研究訊號帳本：適合做系統學習，不適合直接當單次決策依據；需要明確標樣本數、來源集中度、alpha 定義與信心水準。

五維度裡，風控最成熟；籌碼有每日節奏但需要補「金額 vs 股數、資料日期、法人是否同向、與價格動能是否衝突」；左側有 L-Score 但還偏候選清單，缺 thesis、催化劑、失效條件與穩定更新；右側最弱，因 IOS-MOMENTUM 近期獨立輸出未驗證，現有股期戰術也不足以覆蓋「題材+產業鏈+成交+位階+失敗條件」；新聞層也弱，因 on-demand 與 DB 事件尚未穩定轉成 Owner 可讀判斷卡。

世界觀/終局層是最大缺口。這不是多做一份宏觀報告，而是 Owner 四層篩選的第一層缺席：沒有先定義「哪個三年以上大趨勢值得觀察、瓶頸在哪、什麼證據會證實或證偽」，後面的左側、右側、籌碼、新聞都會變成事件追逐。

**2. 循環設計建議**

Claude 的 Goal-Signal-Decision-Review 方向正確，但盲點是：`investment_goals.md` 如果只是季度文件，很容易變成第 21 個沒人看的輸出。它必須變成所有報告的 schema anchor，而不是另一本說明書。

目標定義不要只寫績效目標，否則會誘導事後合理化。建議拆成三種目標：

- 風控目標：最大回撤、現金/曝險區間、集中度上限。
- thesis 目標：本季只驗證 1-2 個終局假設，每個有證實條件與證偽條件。
- 流程目標：哪些訊號品質要改善，例如資料新鮮度、來源分層、右側失敗條件完整率。

訊號標籤不能強迫每個訊號都掛 goal_tag。需要允許 `no_goal_match` 或 `radar_only`，否則會把雜訊硬塞進目標，變成敘事污染。

季度覆盤適合檢討世界觀與曝險結構，但太慢，不適合右側與資料品質。建議三層節奏：每日校準保留在財經早報，週度檢查訊號品質與資料 stale，季度才檢討 thesis 是否證實/證偽與目標是否調整。

還缺一個「決策紀錄契約」：不一定是買賣動作，也可以是觀察、等待、排除、降低信任。每筆決策都應記錄目標、訊號、判斷類型、預期驗證時間、失效條件、資料可信度。

**3. 分階段優先序**

如果只能先做一件事，建議先修 nightwatch / 治理監控 / 資料新鮮度 gate，而且範圍要窄：先恢復「哪些資料真的新、哪些 job 只是 exit=0、哪些輸出不可用」的可信判斷。

理由：現在已有錯誤 184 證明 job 成功不等於資料更新，且 nightwatch 自 2026-06-02 後停擺。若先建 goal file 或 goal_tag，會把 stale data 包裝成很漂亮的複利循環，反而更危險。Goal-Signal-Decision-Review 的第一個前提不是目標文字，而是訊號可信。

建議順序：

1. 先恢復 nightwatch / freshness gate：讓每個決策輸出知道自己可不可信。
2. 再建一頁式 `investment_goals.md`：只放本季曝險目標、最大回撤、1-2 個 thesis、證實/證偽條件。
3. 先接兩個 pilot：財經早報與曝險帳本加 goal/freshness 對照，不要一次改 20 個輸出。
4. 再補世界觀/終局層：做成「thesis registry + evidence ladder」，不是每日長文。
5. 最後才做 Dashboard 目標分頁；否則只是把尚未驗證的流程視覺化。
