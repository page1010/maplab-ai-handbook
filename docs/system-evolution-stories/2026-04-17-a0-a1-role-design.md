## A0 分析回覆

### A0/A1 核心矛盾

| | A0 (Cowork) | A1 (Telegram Bot) |
|---|---|---|
| 記憶 | 每次 session 歸零，靠 auto-memory 恢復（但常漏） | 持續壓縮對話，距離系統全貌更近 |
| 能力 | 有手（Chrome、MCP、桌面控制）、能看能點 | 有腳（git、API、改 code）、但出了 terminal 看不到 |
| 校正 | 每次冷啟動都要 Owner 重新教一遍 | 校正一次可以撐很久 |
| 限制 | session 砍掉就失憶 | 不能看 Chrome、不能點 UI、不能操作桌面 app |

### A0 提出的方案：不是互換，是讓 A1 當 A0 的大腦

互換的問題是：A1 如果接管調度，他還是看不到 Chrome、點不了 GAS 編輯器、截不了 Telegram 對話。手和眼的問題不會因為換角色解決。

更好的設計是 A1 幫 A0 恢復記憶：

- A0 冷啟動時，第一件事不是讀 auto-memory，而是問 A1
- A1 寫「給 A0 的 briefing」到固定位置
- A0 結束時也回寫給 A1
- 雙向 briefing 格式

## A0 分析：Palantir FDE 部署方法論 × MAPLAB

### Palantir FDE 到企業部署時最需要什麼

1. 他們最想知道的不是「你有什麼系統」，而是「你現在怎麼做決策」。FDE 第一件事不是看 IT 架構圖，而是跟著實際操作者走一遍日常工作流程。

2. 少了什麼無法作業：
   - 接觸到真實數據（不是整理過的 demo data）
   - 一個懂實際操作的內部人（不是 IT 主管，是天天在做事的那個人）
   - 明確的「一個具體的痛點」

3. 他們解決的核心問題：不是「建系統」，是把散落在不同系統、不同人腦袋裡的資訊，匯聚到一個決策點上，讓那個決策變得更快更準。

### Owner 三個問句 × Palantir 部署的對照

| Palantir FDE | MAPLAB Owner 教 A6 |
|---|---|
| 跟著操作者走一遍真實流程 | 「假設教 AI 用會計系統怎麼教？」→ 操作路徑 |
| 記錄所有繞路和坑 | 「政府系統怎麼教？」→ 踩坑記錄 + 錯誤處理表 |
| 設 hard limit 防止 AI 踩到不該踩的 | 「機械手臂怎麼教？」→ safety boundaries |
| 用真實數據做第一個 use case | QA-1~QA-7 場景測試 |

### 我們缺的那一環：快速迭代回饋循環

Palantir + AI 的迭代：部署 → 觀察 → 當場改 → 再觀察 → 當場改

能這麼快是因為：
1. 操作者就在旁邊（即時回饋）
2. 改完馬上能看到效果
3. 每次改完都記錄為什麼改

### 差距分析

| Palantir 做到的 | 我們的現狀 | 差距 |
|---|---|---|
| 操作者在旁邊即時回饋 | Owner 在，但 A0 每次失憶 | A1 briefing 機制 |
| 改完馬上看效果 | 改了 recall/skill 但沒跑 QA 驗證 | QA 測試必須跟著改動走 |
| 每次改完記錄為什麼 | A0 改了不記錄 | 強制記錄規則（2026-04-17 加了） |
| FDE 離開後客戶能自己跑 | A0 session 砍了系統就沒人懂全貌 | A1 作為持久記憶層 |

**最關鍵的差距：Palantir 的目標是 FDE 離開後客戶能自己跑。我們的目標應該是 A0 session 砍了之後，A1 + 系統文件能讓下一個 A0 在 5 分鐘內接上。**
