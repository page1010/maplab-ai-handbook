## Executed runtime contract

### Secure copy and ledger

- Each ancestor is opened relative to an already trusted directory descriptor
  with `O_DIRECTORY` and `O_NOFOLLOW` where the platform provides them.
- Sources must be regular, single-link files. Symlink ancestors, hardlinks and
  FIFOs are rejected before payload streaming; source inode, size, timestamps
  and link count are rechecked before the copy is accepted.
- Destinations use `O_CREAT | O_EXCL | O_NOFOLLOW` and mode `0600` inside
  synthetic mode-`0700` roots.
- The copy loop hashes and counts streamed bytes. The destination is reopened,
  rehashed and recounted. The ledger records both digests, exact size, logical
  path and target mode; it accepts no caller or legacy manifest digest.
- `_ledger.json` and `_SEALED.json` are exclusive files written after the
  artifacts. An active generation must have a valid matching pair; every read
  rechecks its artifact against the ledger.

### Publication, recovery and durability

- A generated copy remains under a unique staging name until all artifact,
  ledger and seal writes have completed. Under the publication lock, the final
  generation directory is then created exclusively and populated from the fixed
  ledger; a plain replace-capable directory rename is not used. The active
  pointer, not directory creation, is the publication boundary.
- Injected `EXDEV` is handled only for generation import: the fixed logical
  artifact list is copied into a fresh destination-side generation, rehashed,
  sealed and then published. The active pointer is never streamed in place.
- Every artifact, ledger, seal and pointer file is actually `fsync`ed; the
  relevant parent directory is `fsync`ed after publication. Instrumentation is
  recorded only after the real call returns.
- The active pointer is a regular JSON record containing generation, monotonic
  epoch and a durable authoritative-write barrier. CAS requires both expected
  generation and expected epoch, preventing stale and ABA-style publication.
- Before the write barrier, CAS rollback may select a prior sealed generation.
  `begin_authoritative_write` persists the barrier before any new write is
  allowed. After that barrier, even a fresh resolver instance keeps the current
  generation authoritative and returns `FORWARD_REPAIR`; it never selects a
  repository fallback.

## What this does not prove

- Temporary-root ownership and mode checks do not harden or even re-read the
  current Case Store, bot/provider config, Hermes training, review, dispatch or
  backup roots. Current private roots therefore remain `owner_only=false`.
- Injecting `EXDEV` proves the fallback branch, not a real different-filesystem
  migration.
- Executing `fsync` establishes ordering and error propagation, not survival of
  a real power loss.
- Synthetic threads do not prove live writer quiescence or multi-process
  production locking.
- No consumer was patched. No SQLite backup, `quick_check`, schema/count/hash
  comparison, provider-key cutover, 53-artifact live copy, backup-schedule
  change, service restart or launchd readback occurred.
- Apps Script / Google was not called. Quote/LINE deployed source, the Orders /
  OrderCharges writer and a header-capable LINE ingress remain unresolved.
- No credential, environment, LINE, customer, quote, photo or delivery payload
  was read. Network, model, customer send, publication and price writes remain
  zero. Confirmed leakage remains `0` until the evidence join closes.
- The backup helper in G1 is only a logical-surface/repository-token guard. It
  does not classify env, Case Store, adapter, 53-item non-adapter, dispatch or
  backup-index paths. That zero-sensitive classification is deliberately G2.
