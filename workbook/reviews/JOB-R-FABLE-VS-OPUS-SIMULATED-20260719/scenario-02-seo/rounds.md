# 場景 R03：SEO 優化 — 5 輪推理

場景定義：Local SEO Factory 56 篇文章歸屬 + Catering Matrix 重啟。
執行日期：2026-07-19
模型替代：Fable ≈ claude-sonnet-4-6（策略執行導向）｜Opus ≈ claude-opus-4-7（深度推理導向）

## 第 1 輪（初始探索）

### Fable 視角（策略執行導向）

SEO 問題的核心是執行落地，不是策略設計。Local SEO Factory 56 篇文章如果「歸屬未定」，實際影響是：Google Search Console 數據無法對應到正確的內容負責人，優化循環斷鏈。80/20 原則告訴我們：56 篇裡大概有 10-12 篇帶走了 80% 的流量，先搞清楚這 10-12 篇的歸屬，剩下的可以批量處理。

Catering Matrix 重啟的優先級：根據 CURRENT_STATUS 中提到的 JOB-A2-SEO-CATERING-COMPETITOR-MATRIX-20260617，這個任務已經存在過一次啟動記錄。重啟前需要確認：①前一次停止的原因是什麼？②現有資料是否還有效？③重啟的目標相比第一次有沒有變化？這三個問題不確認就重啟，等於白做。

可執行第一步：從 GSC 提取 56 篇文章的點擊量排序，前 20% 先標記。這個動作不依賴任何人工審查，可以直接自動化。對應的文章歸屬邏輯：外燴主題歸 A2、一般餐廳主題歸 B1-SEO、投資相關歸 IS-team。

工具可用性評估：MCP google-search-console 可用，可以直接執行 search_analytics 查詢。這是 W 層級動作。

### Opus 視角（深度推理導向）

「56 篇文章歸屬」這個問題的表面定義可能是錯的。「歸屬」可能是指：①哪個 agent 負責維護？②哪個業務線的 SEO 策略？③哪個目標受眾的關鍵字叢？這三種定義導致完全不同的分類邏輯。在沒有確認定義前，任何分類動作都可能是在解決錯誤的問題。

Catering Matrix 的深層問題：「Matrix」這個詞本身就值得質疑。它是一個「競對分析矩陣」還是「內容結構矩陣」還是「關鍵字攻佔矩陣」？不同定義對應不同的數據需求和執行週期。從 JOB-A2-SEO-CATERING-COMPETITOR-MATRIX-20260617 的命名看，傾向是競對分析，但需要讀原始任務卡確認。

SEO 優化的系統性盲點：Local SEO 和一般 SEO 在演算法權重上差異很大。Local SEO 最重要的信號是：Google Business Profile 的完整度、NAP 一致性（Name/Address/Phone）、本地評論數量和回覆率。如果 56 篇文章的 SEO 優化方向是衝長尾關鍵字，但 GBP 數據很差，優化效果會大幅打折。這個跨信號的連動影響，在單純看文章歸屬時很容易忽略。

不確定標示：目前不確定 56 篇文章是否已有 URL 清單，或只是數量估計。這直接影響接下來能做什麼。

## 第 2 輪（治理準則過濾）

### Fable 視角

批判第 1 輪：提出「前 20% 先標記」是對的方向，但跳過了準則 ① 先對齊——需要先確認 Owner 對「歸屬」的定義是什麼。如果 Owner 的歸屬定義是「哪個 agent 維護」，那從 GSC 流量排序切入是對的；但如果是「哪個業務線」，切入點就不同。

治理準則逐條對照：
- ③ 驗證優先：56 篇是確定數字還是估計？需要先從 GSC 或 WP 後台確認實際文章數。
- ⑤ 結論帶證據鏈：Catering Matrix 重啟前，要附上第一次停止的 commit 記錄作為歷史依據。
- ⑦ 修根因：如果文章歸屬問題是因為「建立文章時沒有要求填寫負責人 tag」，修法是改文章建立 SOP，而不是事後一篇篇核對。
- ⑧ 落檔：56 篇文章的歸屬分類結果，存入 Sheets 讓後續巡查自動化。
- ⑩ 問題格式：問題=文章歸屬未定；成因=建立流程無負責人欄位；解法=補 tag 機制 + 一次性回溯；選項 A=只補高流量前 20%，選項 B=全量補。

### Opus 視角

批判第 1 輪的「Matrix 定義質疑」：雖然這個質疑邏輯上正確，但在這個場景下，質疑定義的成本高於直接確認定義。更有效的路徑是：先讀 JOB-A2-SEO-CATERING-COMPETITOR-MATRIX 任務卡，用 5 分鐘確認定義，而不是花一輪推理在「可能是什麼」上。這違反了準則 ③（驗證優先於宣稱）。

更重要的 SEO 系統盲點：Local SEO Factory 的「Factory」含義是批量內容生產，但批量生產有兩種失敗模式：①技術 SEO 正常但內容質量差（Google 不分發）②內容質量正常但技術 SEO 錯（被 canonical 或 noindex 蓋掉）。56 篇文章的狀態診斷需要同時看這兩個維度，不能只看流量。

Catering Matrix 重啟的系統性建議：任何「重啟」任務都應該先回答「為什麼第一次停止」，這不只是準則 ⑦（修根因）的要求，也是避免在同樣問題上反覆投入資源的基本原則。從 commit 歷史看，JOB-A2-SEO-CATERING-COMPETITOR-MATRIX-20260617 停止的原因應該可以追溯——需要讀那個任務卡。

## 第 3 輪（交叉批判與收斂）

### Fable 視角

接受 Opus 的「驗證優先於質疑」修正。在這輪，把注意力放在可執行路徑的收斂：

SEO 行動路徑收斂（三步驟）：
1. 數據確認（W 層，今天做）：用 GSC MCP 提取實際文章清單 + 流量數據，確認是否真的 56 篇，以及高流量前 20% 是哪些
2. 歸屬定義確認（SW 層，提交後等 Owner 回覆）：製作一個 30 秒可回覆的選項卡，問 Owner：文章歸屬 = A/B/C 哪種定義？
3. Catering Matrix 讀舊任務卡（W 層，5 分鐘）：確認第一次停止原因，再決定重啟範圍

這三步的依存關係：步驟 1 和步驟 3 可以平行執行，步驟 2 的回覆決定步驟 1 結果的處理方式。

Catering Matrix 重啟的最小可行版本：如果第一次停止是因為數據缺口，重啟需要先解決數據源。如果是因為人力缺口，重啟需要先確認 A2 的當前可用 bandwidth。

### Opus 視角

第 2 輪的系統性批判仍然停留在「提問」層次，沒有給出分析框架。這輪嘗試建立 SEO 健康度的多維評估框架：

Local SEO 健康度的四個信號層：
1. 技術層：crawler 可達性、canonical 設置、Core Web Vitals
2. 內容層：E-E-A-T 符合度、目標關鍵字密度、內部鏈結結構
3. 本地信號層：GBP 評分、NAP 一致性、本地 citation 數量
4. 行為信號層：CTR（GSC）、平均停留時間（GA4）、轉換率

56 篇文章的「歸屬」問題，在這個框架下的意義更清楚：不同信號層需要不同角色負責。技術層由 B1 負責、內容層由 A2 負責、本地信號層由 A4/GBP 負責、行為信號層由 A6/A2 共同分析。所以「歸屬」其實是一個多 owner 的矩陣，不是單一歸屬。

Catering Matrix 的連動：如果 Catering Matrix 是競對分析，那它的輸出應該直接影響內容層的關鍵字策略。這意味著 Catering Matrix 重啟的優先級取決於內容層當前的缺口有多大。

## 第 4 輪（深化與收斂）

### Fable 視角

Opus 第 3 輪的四層框架很有價值，但需要轉化為行動分工。基於四層框架，56 篇文章的歸屬分類可以直接按技術/內容/本地/行為四層切：

實際執行計畫：
- 技術層歸屬：自動化（GSC 爬蟲狀態 + Search Console 索引狀態）
- 內容層歸屬：A2 負責所有外燴相關文章，B1 負責通用內容
- 本地信號層：A4 負責 GBP 連動文章（帶地址/電話的頁面）
- 行為信號層：A6 負責有轉換意圖關鍵字的文章（外燴詢價類）

這個分類邏輯的好處：可以用文章 URL 或 slug 自動判斷，不需要人工一篇篇讀。

Catering Matrix 重啟的明確條件：確認四層框架中「內容層關鍵字策略」是否有缺口。如果前 20% 高流量文章已覆蓋主要外燴關鍵字，Catering Matrix 可以降優先級；如果有明顯空白，則需要重啟來填補。

### Opus 視角

四層框架帶來了一個新問題：多 owner 矩陣在實際執行時會產生「責任分散」效應——每個人都覺得是別人的責任，最終沒人負責。Local SEO 的跨信號協作需要一個明確的整合角色。

建議：A2 擔任 Local SEO 整合角色（Lead），對四層信號的綜合健康度負責，其他角色（A4、B1、A6）提供各自信號層的數據，但不直接做決策。這個角色設計需要在 T-A2-* 任務卡中明確，否則仍會分散。

Catering Matrix 的深層定位：Catering Matrix 不只是 SEO 工具，它其實是 MAPLAB 業務定位的映射——「我們在外燴這個關鍵字生態裡佔什麼位置」。這個戰略意義讓它的優先級比單純 SEO 任務高一個等級，應該由 Owner 親自確認重啟方向，而不只是 A2 自行決定。

Local SEO Factory 的根本邏輯：「Factory」暗示的是可複製的生產模式。56 篇文章如果是用同一套模板批量產生的，那它們的問題也會是系統性的，不是個別文章的問題。最有效的介入點是「Factory 模板」本身，而不是逐篇修改輸出。

## 第 5 輪（最終精煉）

### Fable 視角

整合四輪推理，給出 SEO 場景的最終可執行輸出：

問題：56 篇文章歸屬未定 + Catering Matrix 重啟條件不明確
成因：①文章建立 SOP 無負責人欄位 ②Factory 模板問題可能導致系統性 SEO 缺陷 ③Catering Matrix 第一次停止原因未文件化
解法：
- 選項 A（最小成本）：只處理前 20% 高流量文章，補 owner tag，其餘批量按 URL 規則自動分類
- 選項 B（系統修根因）：修 Factory 模板，加 owner 欄位 + 關鍵字層標記，新文章自動歸類；舊文章用 script 回溯

Catering Matrix 重啟決策樹：
1. 讀舊任務卡確認停止原因
2. 如果是數據缺口 → 先填數據再重啟
3. 如果是人力缺口 → 確認 A2 bandwidth 再重啟
4. 如果是方向不明 → 提 NW 給 Owner 確認戰略定位

第 1 輪 vs 第 5 輪的最大進化：第 1 輪認為問題是「文章沒有分類」，第 5 輪確認問題是「Factory 模板缺少 owner 欄位，導致批量問題無法批量修」。解法從「篇篇標記」升級為「修模板，讓問題不再出現」。

### Opus 視角

SEO 場景最終洞察：Local SEO Factory 的「Factory」模式本身是一個雙面刃。批量生產降低了每篇文章的邊際成本，但也意味著模板缺陷會被放大 56 倍。最重要的治理動作不是「管理 56 篇文章」，而是「管理生成這 56 篇文章的流程」。

Catering Matrix 的最終定位確認：這個矩陣的真正價值是「關鍵字攻佔地圖」，告訴 A2 哪些外燴關鍵字尚未被 MAPLAB 或競對覆蓋。它是一個戰略工具，而不是一個 SEO 執行工具。因此，它的輸出不應該直接是文章，而應該是「優先攻佔的關鍵字清單」，由 Factory 流程接手生產。

Local SEO 的最終系統性建議：建立一個「Local SEO 健康度儀表板」，整合 GSC + GA4 + GBP 數據，讓 A2 每週有一個 5 分鐘的巡查入口，而不是依賴人工觀察。這個儀表板如果能接 Sheets，可以讓 A0 自動派工給相關角色。

對 W→SW→NW 的應用：Catering Matrix 重啟是 NW 層級（戰略工具，需 Owner 確認方向），文章歸屬分類是 W 層級（執行性分類，不影響業務方向）。
