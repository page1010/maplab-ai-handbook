# 報價計算與菜單組合邏輯（業務真實思路）

> **來源**：Owner 2026-04-09 親口說明。
> **優先級**：硬性需求。任何「自動推品項 / 自動算報價 / A6 自動化」邏輯都要對齊本文。
> **目的**：把業務腦子裡的隱性知識變成系統可執行的規則。最終目標是 A6 被訓練到「業務口頭講一句話就能半自動產出符合這個邏輯的報價」。

---

## 核心硬性指標

| 指標 | 規則 | 為什麼 |
|------|------|--------|
| **毛利率** | **≥ 70%** | 報價底線。低於這個數字基本上不接 |
| **單人取餐量** | **約 4 樣** | 自助式 buffet 取餐量估算基準 |
| **總件數** | **人數 × 4 ± 視情況調整** | 由單人量推算 |
| **類別平衡** | **甜 / 鹹各佔一半左右**（點心類） | 視覺豐盛 + 適合不同口味客人 |
| **品項種類** | **越多種越好**（在預算內） | 擺盤漂亮、看起來豐盛、給客人選擇 |

---

## 業務的實際思路（Owner 親口說的場景）

**情境輸入：** 預算 15,000 / 30 人 / 總件數 120

**業務腦內的計算過程：**

1. **先算單人量**：30 人 × 4 樣 = 120 件 ✓ 對到客戶要求
2. **再決定品項數**：為了擺盤漂亮 + 種類多 → 拆 8 個品項（不是 6 個或 10 個，是 8）
3. **甜鹹比例**：甜 4 + 鹹 4，平均
4. **每品項的量分配（120 件 / 8 品）**：不是均分 15，而是依品項屬性微調：

   ```
   品項 1: 10 件（成本高的少出一點）
   品項 2: 15 件
   品項 3: 15 件
   品項 4: 10 件
   品項 5: 15 件
   品項 6: 15 件
   品項 7: 20 件（成本低的多出一點）
   品項 8: 20 件
   ────────
   合計: 120 件 ✓
   ```

5. **算成本**：每品項的 default_cost × 數量加總 → 例如 15,000 × (1 - 0.7) = 4,500 上限
6. **驗毛利**：(15,000 - 4,500) / 15,000 = 70% ✓ 符合底線

## 從業務思路抽出的系統規則

### 規則 1：總件數推算
```
total_items = pax × 4   // 預設係數 4，可由 form 的 totalItems 欄位覆蓋
```

### 規則 2：品項數量決策（80/20 原則）
```
if pax ≤ 20:        item_count = 4–5
elif pax ≤ 50:      item_count = 6–8
elif pax ≤ 100:     item_count = 8–12
else:               item_count = 10–15
```
**設計原則**：寧可品項數多一點，不要每樣量太少。漂亮優先。

### 規則 3：甜鹹比例（依活動類型）
| 活動類型 | 甜點 % | 鹹食 % | 主食 % | 飲品 % |
|----------|--------|--------|--------|--------|
| 週歲 / 性別揭曉 / 個人慶生 | 50 | 35 | 5 | 10 |
| 婚禮 | 30 | 40 | 15 | 15 |
| 企業 / 開幕 / 尾牙 | 25 | 45 | 15 | 15 |
| 新居入厝 | 40 | 40 | 10 | 10 |

### 規則 4：成本上限（毛利 70% 反推）
```
max_cost_total = budget × (1 - 0.70) = budget × 0.30
```
任何品項組合的 total cost 超過 max_cost_total 就要砍量或換便宜品項。

### 規則 5：每品項數量分配（非均分）
- 預設：均分 = total_items / item_count
- 微調：成本高的減 1/3、成本低的加 1/3、其他保持均分
- 微調後：所有品項數量總和必須仍等於 total_items（誤差 ≤ 5）

### 規則 6：擺盤豐盛優先
寧可：8 品 × 15 件 = 120 件（看起來豐盛）
也不要：4 品 × 30 件 = 120 件（單調）
這是視覺體驗優於成本最佳化的硬規則。

## 對 A6 / createQuote 的具體實作含義

當業務在 Telegram 講「報價 王小明 婚禮 80人 預算 35000」，A6 應該：

1. 算 total_items = 80 × 4 = 320 件
2. 算 max_cost = 35000 × 0.30 = 10500
3. 看活動類型 = 婚禮 → 甜 30% / 鹹 40% / 主食 15% / 飲品 15%
4. pax 80 → item_count 8-12，挑 10
5. 從 Items 表選：3 甜點 + 4 鹹食 + 2 主食 + 2 飲品（飲品其實 1-2 大桶就好，不算入 10 品）
6. 做數量分配：高成本品項減量、低成本加量
7. 驗證 sum(qty × cost) ≤ 10500，否則砍貴品項
8. 寫入 QUOTE_DRAFT D7:F19，產出 copy
9. 在 SALES_INTAKE 寫入 case_id + 預估毛利 + 推薦理由

業務拿到的是「填好品項數量的草稿」，而不是「填好客戶資料但品項全空的殼」。

## 車馬費規則（2026-04-09 Owner 定義）

**公式**：
```
if (Google Maps 導航時間 < 30 分鐘) → 車馬費 = 0
else                                → 車馬費 = ceil(單程距離 km) × NT$6
```

**起點**：MAPLAB 台南和緯店（實際地址 Owner 待確認，`quoteHelpers.gs` 的 `MAPLAB_ORIGIN_ADDRESS` 常數）

**驗證**：
- 台南市內（大部分）→ 導航通常 < 30 min → **$0**
- 嘉義 → 導航 ≈ 50-60 min、單程 ≈ 65 km → $390
- ⚠️ 歷史 sample `2025/1/4 曹家瑄 嘉義` 車馬費為 $3,000，跟 $6/km 公式差 $2,610。可能是舊版定價或有 base fee，**Owner 待確認**。

**實作**：`scripts/apps-script/quoteHelpers.gs` → `calcTransportFee(address)`
- 用 Apps Script `Maps.newDirectionFinder()` 查路線
- 回傳 `{ fee, distanceKm, driveMin, method, note }`
- createQuote 自動寫 E27（車馬費 cell）+ L11（計算備註）

## 搬運費規則（2026-04-09 Owner 定義 + sample 驗證）

**公式**：
```
2F 無電梯 + 有人協助 → $500
2F 無電梯 + 無人協助 → $1,000
其他（平面 / 有電梯）  → $0
```

**實作**：`scripts/apps-script/quoteHelpers.gs` → `calcFloorFee(mode)`
- QuoteForm 加 `floorFeeMode` select（三選一）
- createQuote 自動寫 E28（搬運費 cell）+ L12（mode 備註）
