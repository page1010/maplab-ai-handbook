## 1. 讀懂 Polsia

### ① 他怎麼讓 agent 做完 80% 的工作（架構／流程／人機分工）

Polsia 的本體是一組 **9 個專職 agent 的編排系統**，人機分工是「人給一句想法，系統把公司開起來」：

- **Orchestrator（總調度）**：規劃當天要做什麼，把任務分給其他 agent。
- **Social agent**：發社群貼文。
- **Outreach agent**：寄陌生開發信（cold email）。
- **Support agent**：回信箱／客服。
- **Ads agent**：管 Google／Meta 廣告。
- **Finance agent**：追 Stripe 金流。
- **Planning / Competitor research / On-demand code**：規劃、競品研究、按需寫程式。

流程（這是他 80% 自動化的真正機制，重點在**環境自動供裝**）：使用者打一句想法、或按「Surprise me」→ 系統**自動開好伺服器、Stripe 帳戶、email 信箱、GitHub repo**，然後就開始「launch」。

換句話說，他不是「一個超強 agent」，而是**把一家公司的骨架（金流、網站、信箱、廣告、客服）先自動搭好，再讓多個窄 agent 各跑一段**。人只在最前面給意圖，其餘由系統跑——這是他敢說「0 員工做 80%」的來源。**但要誠實**：客訴顯示「跑起來 ≠ 跑對」，自動化覆蓋率高、可靠度低。

### ② 他的系統具體能做什麼（產品功能）

一句話：**「想法 → 一間會自己運作的公司」的自助生成器。**
- 自動供裝營運基礎設施（server / Stripe / email / GitHub）。
- 自動做行銷（社群、陌生開發、廣告）、客服、金流追蹤、按需寫程式。
- 全程自助（self-serve），刷卡即用，沒有真人 onboarding。

### ③ 為什麼大家願意付費——核心價值（他到底在賣什麼）

**他賣的不是「可靠的結果」，也不是「省人力」本身。他賣的是三件事的組合：**

1. **把「想法 → 上線」這段距離壓到最短（access + speed）。**
   一般人從想法到「有網站、有金流、有在跑廣告」要花數週、要會很多工具。Polsia 讓你刷 $49 就跨過這條線。**他賣的是跨越啟動門檻的門票，不是跨越後的品質。**

2. **產品化 + 自助分發（distribution）。**
   $49/月 起、20% 分潤、刷卡即用、零 onboarding。低到「值得試一次」的入場價，加上「0 員工做出 80 億公司」這個**創辦人敘事本身就是行銷**，形成自助漏斗。他把「請一個團隊」變成「開一個訂閱」。

3. **敘事與想像（narrative）+ 平台鎖定（lock-in）。**
   「零員工公司」的夢賣得動願意賭一把的人；而網站／網域／程式被綁在他自家基礎設施上，**要搬走很難**——這是他真正的護城河之一，不是技術，是鎖定。

> **核心價值一句話**：Polsia 賣的是「**產品化、自助、低價的『想法→上線』加速器 + 敘事**」，用可跨越啟動門檻的**速度與 access** 收費，而**不是**用可靠的交付結果收費。85% 的次月留存說明對「低風險、想快速把東西弄上線」那群人確有效用；1.9 的評分說明對「要真的穩定營運」的人不夠格。**這個落差，正是我們對標時要偷的東西與要避開的坑。**

## 2. 拆解商業模式

**可複製的產品化在哪：** 把「開一家公司要做的事」拆成標準化步驟（供裝基礎設施 → 行銷 → 客服 → 金流），每步交給窄 agent，包成一個自助介面。可複製性高——真正難的不是 agent，是**把它做成不需要真人帶、刷卡即用的產品**。

**如何規模化到 0 員工 × 上萬客戶：**
- **自助（self-serve）**：沒有真人 onboarding，邊際服務成本趨近 0 → 客戶數不受人力限制。
- **基礎設施自動供裝**：每個新客戶的環境由程式開，不靠人。
- **敘事飛輪**：創辦人故事本身帶流量，降低獲客成本。

**定價：** $49/月 base + **20% 營收分潤**。分潤把「工具」重新定位成「幫你建的事業的合夥人」，也讓少數成功客戶貢獻不成比例的收入。

**護城河（誠實排序）：**
1. **平台鎖定**（網站/網域/程式綁在他家）——最硬，但也最被客訴。
2. **分發與敘事飛輪**——難複製。
3. **產品化的自助流程**——可被複製。
4. 技術（多 agent 編排）——**護城河最淺**，人人可做。

> **對我們最重要的一句**：他的護城河是**分發 + 產品化 + 鎖定**，不是模型或 agent 技術。所以我們若要學，要學的是「產品化與分發」，不是再堆一層 agent。

## 3. 對標我們（MAPLAB OS）——誠實列不足

### 我們現在是什麼（先講清楚，才對得準）

讀 `CURRENT_STATUS.md`、`README.md`、`SYSTEM_DIRECTORY_INDEX.md` 後：MAPLAB OS 是**一套對內的多 agent 營運系統**，服務對象是 **MAPLAB Kitchen（台南高階外燴品牌）+ Owner 的投資（Investment OS）**。強項很明確：**治理與記憶（索引、交接、pitfalls、review bundle）、自我驗證文化、成本紀律（地端模型省 token）、對內自動化迴圈（Cashflow Loop、Investment Loop）**。

**但這裡有個根本差異，對標時不能裝作沒有：Polsia 是『把 agent 系統當商品賣給上萬人的產品公司』；MAPLAB OS 是『一個品牌 + 一個 Owner 自用的內部系統』。** 兩者不是同物種。所以下面不是要我們變成 Polsia（何況他 Trustpilot 1.9），而是誠實照出**結構性空白**。

### 我們相對他的不足（誠實、有據）

1. **沒有對外產品、沒有外部付費客戶、沒有 ARR。**
   我們的 agent 系統 100% 內部用。Polsia 把 agent 系統**賣出去**；我們把它**自己用**。外部營收 = 0，這是最大的結構性空白。

2. **沒有自助分發（no self-serve distribution）。**
   沒有註冊、沒有 onboarding-free 的入口、沒有「陌生人刷卡即用」的漏斗。要操作 MAPLAB OS 得靠 Owner + 一本厚 handbook。Polsia 是「打一句話就上線」，我們是「先讀冷啟動 SOP」。

3. **沒有閉環自動交付；幾乎每件事卡在『等 Owner 核准』。**
   大量迴圈終點是「草稿，未發布，等 Owner」。`CURRENT_STATUS` 自己記錄：NEEDS_REVIEW 10 張任務卡等 Owner ~256h、T-A7-001 Phase 3 逾期第 11 天、T-A4-002 ~2489h、T-IOS-KOL-001 ~977h、A6 ~514h。Polsia（就算會出錯）是**自動 ship**；我們是**把幾乎所有事前置在 Owner 身上**。

4. **Owner 是單點瓶頸——這其實是「0 員工」的反面。**
   Polsia 是 0 員工 × 系統自動跑；我們是 **1 Owner 卡住整條線**。多條關鍵任務停滯數百到數千小時，根因是「等一個人決定」。

5. **Agent 真實可用率誠實偏低，還不到可交付門檻。**
   `SYSTEM_DIRECTORY_INDEX.md` 自己揭露：A6 回覆模型 gym 實測可用率約 **0%–20%**，而大家記憶中的「8 成」其實是 **A5 報價毛利率，不是模型準確率**。所以連「對內自動交付」都還沒到可靠。

6. **累積了大量能力，卻沒有一項被打包成可販售資產。**
   報價引擎（能產 Google Sheet 報價、算毛利）、SEO + 案例產線、照片分類/命名產線、回覆訓練資料集——每一項都很值錢，但**沒有一項被包成別的中小品牌能買的東西**。

7. **治理很重、對外複利很輕——「忙碌但沒推動複利」的風險。**
   大量規則、巡查、review bundle 是為了對內對齊；相對地，對外可賣、可自動交付的產出接近 0。這正是你自己列的長期風險第 6 條。

> **對標結論（一句話）**：我們在**對內治理與記憶**上比 Polsia 成熟得多、也誠實得多；但在 **產品化、自助分發、閉環自動交付、對外營收** 這四項上是**結構性空白**。差距不在技術，在「**有沒有把能力變成外部有人願意付費、且能自動交付的東西**」。

## 4. 具體改進 + 方法（每項都標「改進後確實能達到什麼」，做不到的標做不到）

原則：80/20，先做一件能驗證「對外」的事，不擴張。不要為了像 Polsia 而去堆 agent。

### 改進 A：挑「一項」能力先產品化，做最小付費驗證
- **做法**：從已有能力挑**報價引擎（A5）**為第一候選（價值最清楚、外燴/餐飲中小品牌對「自動報價」有明確付費意願）。做一個薄薄的自助入口：輸入（人數、預算、活動類型）→ 產出報價 PDF/Sheet。找 1–3 家台南/台灣同業做付費 pilot（固定月費或按報價次數）。
- **改進後確實能達到**：得到「**外部到底有沒有人願意付費**」的第一個實證，消除「從沒對外賣過」這個結構性空白。
- **做不到／不誇大**：短期**不可能**規模化到千客戶（缺分發、缺 onboarding-free、缺品牌敘事）。這一步只證明「能不能賣」，不是「能賣多大」。

### 改進 B：建「一條」可逆的閉環自動交付，把 Owner 從「前置關卡」改成「事後抽查」
- **做法**：挑一條**低風險、可逆**的迴圈，讓它在**預先核准的護欄內**端到端自動 ship，不逐件等 Owner。我們已有 `AGENT_RULES` SECTION 19/24（無人長跑安全規則 + 可逆先行），拿來用。例：A7 客服在**白名單問題類型**內自動回覆、或 SEO 草稿自動發到**低風險/測試頁**。定義成功條件、停止條件、retry budget，改成**事後抽查**而非事前逐件核准。
- **改進後確實能達到**：可量測地**降低 stalled 時數**（現在 NEEDS_REVIEW ~256h、多條 500–2500h），至少一條 loop 的 Owner 介入從「每次」降到「抽查」。
- **做不到／不誇大**：**不會**全系統去人化，也**不該**——投資下單、廣告預算、對外高風險發布仍必須人審。這是刻意保留，不是缺陷。（我們要比 Polsia 更誠實，不是更敢亂 ship。）

### 改進 C：誠實面對可用率，先讓「一個」agent 真的過可交付門檻
- **做法**：挑單一最高槓桿 agent（A6 回覆 或 A5 報價），設一個**真實可用門檻**（如「≥70% 員工可直接送出」），用既有 `a6_gym` eval harness + 真實標註資料迭代，**在過門檻前不擴張範圍**。
- **改進後確實能達到**：把「可用率」從自我宣稱變成**可量測**；拿到「一個 agent 真的可用」的實證，或誠實結論「還不行、差在哪」。
- **做不到／不誇大**：**不保證**達到 Polsia 式全自動——他自己被實測只有 ~21% 成功率。重點是我們過門檻的東西**真的能用**，不是覆蓋率好看。

### 改進 D：把已累積能力做成「產品化候選排序表」
- **做法**：B5 蒸餾已在做能力盤點，加一欄「**對外可販售性**」評分（誰付費、付多少、為什麼），對報價、SEO+案例、照片分類命名、回覆訓練逐項打分，產出一張**排序表 + Top1 的最小商業假設**。
- **改進後確實能達到**：把「該賣什麼」從模糊變清楚，讓改進 A 有依據挑對第一個標的。
- **做不到／不誇大**：清單本身**不產生營收**，只是決策輸入。

### 改進 E：給系統一個「對外北極星指標」，對抗「忙碌但沒複利」
- **做法**：在 `CURRENT_STATUS.md` 頂部新增**一個對外指標**——例如「外部付費驗證數」或「本週閉環自動交付次數（無 Owner 前置）」，每週必報。現有指標（commit 數、patrol、stalled hours）全是對內的。
- **改進後確實能達到**：讓系統每週被迫回答「這週有沒有往『對外能賣、能自動交付』移動一格」，對抗方向漂移。
- **做不到／不誇大**：指標本身**不會自動改善**，要有人或 loop 真的去推它。

## 6. 一個順手提出的小改動（降低未來重工）

**建議先做 E（對外北極星指標），因為它最便宜、槓桿最高**：只要在 `CURRENT_STATUS.md` 頂部加一行「本週對外進展：{付費驗證數 / 閉環自動交付次數}」，就能把整個系統的注意力從「對內巡查」拉一點點到「對外複利」。這一步幾乎零成本，卻能持續提醒每個接手的 agent「別只是忙」。**它不會自己改善，但它會讓『沒進展』無所遁形**——這正是對抗你列的風險第 6 條「忙碌但沒推動複利」的最小介入。
