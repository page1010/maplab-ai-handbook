## 三方意見摘要

### Q1 功能檢討（哪些幫得上/幫不上決策、哪個維度最弱）

| | Codex | Antigravity |
|---|---|---|
| 最強維度 | 風控（曝險帳本+死亡清單+盤後風控+財經早報最接近「今天能不能動」） | 風控（`exposure_ledger.md` 每日更新+生存SOP+最壞情境） |
| 最弱維度 | 右側（IOS-MOMENTUM每日動能簡報未驗證存在）+ 新聞（未穩定轉判斷卡） | 新聞/事件 + 右側動能（同樣點名 IOS-MOMENTUM 缺口） |
| 世界觀/終局層 | 「最大缺口」——不是缺一份宏觀報告，是 Owner 四層篩選的**第一層整個缺席**，後面左右側/籌碼/新聞都變成事件追逐 | 「致命的系統級盲點」——系統直接從第二三層開始輸出，訊號會「失去靈魂」 |
| 其他點名 | Dashboard/Telegram/系統真相地圖偏「入口與治理」不等於決策輔助；夜間簡報/影子教練只能當工作狀態不能當判斷依據；量化資源橋接是參考庫不是決策輸出 | 左側敘事候選更新不穩定（週1-3次）+ 明列缺資料，容易讓 Owner 暴露在用過期數據決策的風險中 |

**共識**：風控最強、世界觀/終局層是最大缺口、右側與新聞層偏弱、Dashboard/Telegram 這類治理/入口層不能誤當決策輔助本身。

### Q2 循環設計建議

| | Codex | Antigravity |
|---|---|---|
| 目標文件風險 | `investment_goals.md` 若只是季度文件會變成「第21個沒人看的輸出」；必須變成所有報告的 schema anchor | 「Dead Document」風險——必須程式碼化，把最大回撤/配比上限直接寫進 `exposure_ledger.md`，讓 Sentinel 每日自動比對 |
| 目標分類 | 拆三種：風控目標/thesis目標/流程目標 | 未細分，但強調要有系統強制力而非人工填寫 |
| 訊號標籤 | 不能強迫每個訊號都掛 goal_tag，需允許 `no_goal_match`/`radar_only`，否則雜訊會污染敘事 | 未提及標籤機制細節，聚焦在目標要「可比對」 |
| 覆盤週期 | 三層節奏：每日校準（已有，財經早報）/週度訊號品質與資料新鮮度/季度thesis證實證偽 | 雙軌制：月度（風控/配比/1R）+ 季度（世界觀/基本面），認為原案季度太慢 |
| 額外建議 | 需要「決策紀錄契約」——每筆決策（含觀察/等待/排除）都記目標/訊號/判斷類型/預期驗證時間/失效條件/信心水準 | 未提及，但隱含在「程式碼化」建議中 |

**共識**：季度單一週期太慢，需要分層節奏；目標文件必須有結構性/程式性的強制力，不能只靠人工維護。**分歧**：Codex 建議週度+季度雙層（訊號品質週度、thesis季度），Antigravity 建議月度+季度雙層（風控月度、thesis季度）——**採納 Codex 的週度版本**，理由是 Owner 的風控語言本來就要求「stale decision」要能被快速抓到，週度比月度更貼近「資料新鮮度」這個高頻檢查項；月度節奏留給風控配比/1R執行率這種較慢變化的項目（等於把兩人的建議合併：風控配比月度、資料/訊號品質週度、thesis與目標季度）。

### Q3 分階段優先序

**兩人給出完全相同的第一步：先修 nightwatch / 治理監控 / 資料新鮮度 gate。**

- Codex 理由：「如果先建 goal file 或 goal_tag，會把 stale data 包裝成很漂亮的複利循環，反而更危險」
- Antigravity 理由：「錯誤184已證明 job exit=0 不代表資料真的更新，nightwatch 停擺一個月，系統處於不知道自己健不健康的盲目狀態」

Codex 進一步給出 5 步順序：① 恢復 nightwatch/freshness gate → ② 一頁式 `investment_goals.md`（本季曝險目標+最大回撤+1-2個thesis+證實證偽條件）→ ③ 先接 2 個 pilot（財經早報+曝險帳本，不要一次改20個輸出）→ ④ 補世界觀/終局層（thesis registry + evidence ladder，不是每日長文）→ ⑤ 最後才做 Dashboard 目標分頁。

**沒有分歧**——直接採納 Codex 的完整 5 步順序，Antigravity 的建議（程式碼化目標、月度風控節奏）併入對應步驟。

## Claude（B1）整合決策

見 `investment-os-functional-audit-2026-07-07.md` 完整方案。核心決策：

1. **不新增第 21 個輸出**——先讓現有 20 個裡最弱的環節（nightwatch）真的活起來，這是解鎖後面一切的前提。
2. **目標文件三分類**（風控/thesis/流程），且從第一天就設計成「機器可讀 schema」而非長文，最大回撤與配比上限直接連結曝險帳本的既有欄位，不重新發明。
3. **訊號標籤允許 `no_goal_match`**，避免為了湊複利敘事硬把雜訊分類進目標。
4. **三層覆盤節奏**：週度（資料新鮮度/訊號品質）、月度（風控配比/1R執行率）、季度（thesis證實證偽/目標調整）。
5. **世界觀/終局層**設計為「thesis registry + evidence ladder」，明確不做成每日長報告（避免變成又一份沒人看的輸出）。
6. **決策紀錄契約**：觀察/等待/排除都算決策，都要留紀錄，不是只有下單才算。
7. 分階段執行順序完全採納 Codex 5 步版本，作為 `handoff/tasks/` 任務卡的依據。
