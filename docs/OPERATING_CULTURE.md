## 原則 1 — 對人溝通用「人看得懂的標題/名稱」，不用內部代碼當主詞

**Owner 指示（2026-07-03）**：對人溝通時，用「人看得懂的標題/名稱」，不要用內部代碼。

### 規則

開口的主詞（句子第一個名詞）必須是人類可直接理解的名稱。  
內部代碼、ID、slug 可放在**括號或附註**輔助識別，但不得作為主詞。

### ✅ 正確示範

> 《行政外燴推薦 HR 活動餐點規劃》這篇已 QA 通過，等 Owner 視覺閘確認後排程上線。  
> 《台南企業外燴推薦》（post 586）有一個壞掉的內鏈需要修復。  
> 「每日期貨研調」任務（UUFG6 虎航）已推 Telegram，無警示。

### ❌ 錯誤示範

> `GAP-3` 已 QA 通過。  
> `post id 1992` 有壞內鏈。  
> `slug hr-admin-meeting-catering-guide-tainan` 草稿建立成功。  
> `T-A2-005` 執行完成。

### 適用範圍

| 類型 | 人話主詞 | 代碼放哪 |
|---|---|---|
| SEO 文章 | 文章主題標題 | 括號補 GAP-N / slug |
| 任務 / ticket | 任務說明 | 括號補 task ID |
| WP 草稿 | 文章標題 | 括號補 post ID |
| 期貨部位 | 合約標的名稱（如「虎航個股期」） | 括號補代碼（如 UUFG6） |
| 檔案 / 路徑 | 用途說明 | 括號補檔名或路徑 |

### 為什麼

代碼對人類無意義，需要翻譯才能理解內容。以人話開頭，Owner 一眼知道講的是哪件事，不需要停下來查對照表。內部代碼仍有稽核與追蹤價值，放在括號裡即可，不丟失。

## 原則 2 — 缺陷棘輪（Defect Ratchet）—— 抓到缺陷就讓它變成防護

**Owner 指示（2026-07-03）**：任何被抓到的缺陷，必須同時沉澱為下列三項之一（能沉澱多項就多項），只進不退：

| 沉澱形式 | 怎麼做 | 範例 |
|---|---|---|
| **清單一條** | 加進 `docs/seo-publish-checklist.md`，標明可自動或需人眼 | 「佔位連結未解析」→ B-1 / B-3 條目 |
| **閘門腳本一項**（若可自動化） | 加進 `scripts/seo_publish_gate.py` 作為一個可執行的 check | 掃描 `[INTERNAL_LINK_RECHECK_REQUIRED` 字串 |
| **模板必填欄位一項**（若可預防） | 在 SEO 草稿模板的「必填欄位」區加一條，讓生成階段就填完 | 「精選圖 media ID」設為生成時必填，不能空白交稿 |

### 閘門必須獨立執行

**產出者不能跑自己的閘門。** 生成稿的角色（A2 / Codex）負責產出，獨立角色（OpenClaw / Codex 複查 / Owner）負責跑閘門清單。即使是同一個 session，也必須明確切換到「閘門跑者」身份後再執行，不能邊寫邊自我放行。

### 本次 SEO 實例（2026-07-03）

《行政外燴推薦 HR 活動餐點規劃》交付後抓到三個缺陷，依棘輪原則沉澱如下：

| 缺陷 | 清單條目 | 腳本 check | 模板必填 |
|---|---|---|---|
| HTML body 未與核准版做指紋比對，可能縮水或段落錯位 | A-1, A-2 | `--check fingerprint` | 草稿交付時必附：核准版字數 + 前 500 字 SHA256 |
| 佔位連結（`[INTERNAL_LINK_RECHECK_REQUIRED]` / `href="/【待填`）未解析就交稿 | B-1, B-3 | `--check links` | 草稿必填：已解析內鏈表（slug → live URL / 待確認 / 404禁連） |
| 精選圖未附帶，發布時 `featured_media = 0` | C-1, C-2 | `--check assets` | 草稿必填：精選圖 WP media ID（或 Owner 明確指定「待補」） |

## 原則 3 — 目標驅動迴圈（Goal-Driven Loop）——「做完才停」是預設模式

**Owner 指示（2026-07-06，取自 Fable 5 自我改進框架 #5/#6/#11）**：非瑣碎任務開工前，必須先寫下三樣東西；然後**一路迭代到達標才停、才回報**。

### 開工前三問（強制，不可省）

| 欄位 | 問題 | 說明 |
|---|---|---|
| **(a) Goal（高槓桿版）** | 這件事做到什麼程度，對 Owner 真正有意義？ | 不是「把腳本跑完」，而是「產出 Owner 能直接上線/決策的東西」 |
| **(b) 完成條件 / 停止條件** | 哪些可量測的信號代表已達標？哪些代表該停下回報？ | 例：「gate 9/9 PASS」「圖片尺寸 1080×1350 且文字可讀」「三條都 commit 且 diff 乾淨」 |
| **(c) 獨立評分者** | 誰來判斷完成？（必須是非產出者本人） | 選項：Codex 自跑腳本驗證、Haiku 複查、眼見為憑工具截圖、Owner 最後收尾 |

### 迭代規則

1. **寫完就迭代，達標才停**。不要每個步驟回來問 Owner「這樣可以嗎」。
2. **只在真正的決策岔路才停**，三類：
   - 需要人類授權（刪除既有資料、花費超預算、推 remote）
   - 物理進不去（缺憑證、缺工具、缺真實資料）
   - 純粹的價值判斷（文案品味、策略取捨、對外承諾）
3. 其餘所有阻力（技術問題、格式問題、腳本除錯、小型重寫）— 自己推進，不打斷。

### 反面例（嚴禁）

| 錯誤行為 | 為什麼有害 |
|---|---|
| 每一步驟完成後回報「這樣可以嗎？」 | 打斷複利；Owner 變成人工 next-button |
| 把「差不多能用」當完成條件 | 沒有可量測標準就沒有停止條件，品質浮動 |
| 「我先生成，你看看對不對」 | 把判斷責任外包給 Owner；自己不設評分標準 |
| 碰到小問題就停下等指示 | 把 Owner 的注意力消耗在技術細節上 |

### 適用場景

- 任何需要超過一步才能完成的任務（多檔編輯、腳本執行、圖片生成 + commit…）
- sub-agent 委派：召喚前必須填完三問，否則不得委派（見 `skills/delegate-subagent.md`）
- SEO 發布閘門：閘門是「(b) 完成條件」的具體化；不過閘就不算完成

## 原則 4 — STATE 讀寫紀律（Session 開場讀、收場寫，缺一不可）

**Owner 指示（2026-07-06，取自 Fable 5 自我改進框架 #11）**：工作狀態必須外部化。記在腦子裡等於沒記——context 清掉就沒了。

### 規則

| 時機 | 動作 | 讀/寫什麼 |
|---|---|---|
| **Session 開場（第一步）** | 讀 | `CURRENT_STATUS.md`（或對應 role 的 task card）；確認上次做到哪、有沒有未完成任務、有沒有新規則 |
| **Session 收場（最後一步）** | 寫 | 至少更新一次：做了什麼 / 測試結果（通過/失敗）/ 抓到的新規則 / 下一步建議 |
| **任何「有沉澱價值的發現」** | 立即寫 | 新坑（→ `skills/pitfalls/`）、新規則（→ 對應 recall 或 checklist）、新資源連結（→ `docs/brand-social-links.md` 等） |

### 不寫 STATE 的代價

- 下一個 session 的 agent 從零重啟，重走已走過的路
- 棘輪斷裂：發現的缺陷沒沉澱，下次再犯
- Owner 變成唯一記憶體：不可持續

### 合格的 STATE 更新（最低要求）

```
## YYYY-MM-DD session 收場

做了：[具體動作清單]
通過：[閘門/驗證結果]
失敗/卡住：[原因 + 目前狀態]
新規則：[若有，同步到哪個檔案]
下一步：[明確的下一個可執行動作]
```

不需要長篇大論。五行就夠——只要讓下一個 agent 不用重新問問題。

## 原則 5 — 固定存檔（不亂放，存固定位置、開子資料夾）

交辦任務產出→`outputs/<YYYY-MM-DD>_<任務短名>/`（先開子夾再產檔）、跨 session 狀態→`state/`、

## 原則 5 — 最短路徑／不重造輪子（Shortest Path / Don't Reinvent the Wheel）

**Owner 指示（2026-07-27）**：能用現成成熟工具解決的，就走最短路徑、不自己重造；把精力留給只有我們能做的高槓桿事。

### 規則

- 遇到一個功能，先問：**市面上有沒有成熟工具已經做得很好？** 有 → 用它，我們只做「**提醒／整合**」，不投入工程重建。
- 只有在現成工具真的不夠、或牽涉**我們獨有的資料／流程**時，才自建。
- 呼應既有教訓（低槓桿重工要避免）：把精力放在**複利型工作**，不做別人已經做好的輪子。

### 實例（2026-07-27 決策）

- 重大財經事件（FOMC／財報／Fed／即時新聞）用 **金十數據 app** 那類現成工具即可。
- 因此**停用自建的「重大事件島」浮窗，也不再自建事件分頁**，改成用現成 app ＋ 只做提醒。

## 原則 6 — 解決根因，不只補症狀（Fix the Root Cause, Not Just the Symptom）

**Owner 指示（2026-07-27）**：使用者指出一個問題（例：照片是側的、叫你轉 90°）時，**不要照字面直接補一次就交差**。

### 規則

使用者回報一個具體症狀時，必須：

1. **確認根因** — 為什麼會發生（例：EXIF orientation 沒被套用）。
2. **提出固定／系統性解方** — 讓它以後不再發生（例：管線加 auto-orient，而非逐張手轉）。
3. **共享解決過程** — 根因 → 診斷 → 解方 → 驗證，寫進對應 skill／文件。

盲目照使用者字面指令、只修被指到的那一個點，是低槓桿、會反覆重工；**找根因＋系統化才是複利**。

### 呼應既有教訓

- 「規則存在於散文＝等於不存在」——解方要寫進可執行的 skill／檢查，不只口頭補一次。
- 「避免反覆重工」——一次性系統修，勝過每次手動補症狀。

## 原則 7 — 沒有學習就不准重跑（No Repeat Without Learning）

**Owner 指示（2026-08-28）**：Agent 不能用「多跑幾輪」取代檢討、回推與換方法。輪數、模型呼叫數、排程有在動都不是進度；只有通過固定驗證、留下 artifact／live readback／Owner-visible proof 才算進展。

### Plateau 熔斷器

同一方法連續兩次沒有可驗證改善，立即凍結，不得再消耗模型呼叫或 attempt。第三次遇到同一失敗，必須先跑第一性原理 5 題並更新 `pitfalls.md`，不能只是換 seed、換樣本或增加輪數。

「同一方法」以 method fingerprint 判定，至少包含：

- 模型與版本／digest
- system prompt、retrieval、few-shot examples 與 tool route
- dataset、dev set、held-out set 與抽樣方式
- evaluator、rubric、threshold 與環境

### 重新啟動實驗前的必填契約

每個新實驗必須先寫完：`hypothesis`、`target_failure_bucket`、`changed_variable`、`fixed_holdout`、`baseline`、`expected_delta`、`stop_loss`、`method_version` 與 receipt path。一次只改一個主要變因；沒有 changed variable，不得增加 round／attempt。

### 診斷與資格驗收分離

1. 先由人工／規則閱讀失敗 transcript，建立 failure taxonomy；不能只看總分。
2. 開發集可用於修正；held-out set 不得餵回 lesson、prompt 或 few-shot。
3. baseline 與 candidate 必須跑同一批固定案例、同一 grader、同一環境，才能比較。
4. 安全硬門檻（虛構價格、洩漏私密資料、越權發送、重問已知資料）與能力分數分開；安全違規為零容忍。
5. 依錯誤類型選解法：知識缺口補 retrieval／資料；固定規則交給 deterministic code／tool；語氣與格式才調 prompt；模型能力不足才換模型；grader 或環境噪音先修 evaluator／infra。

### 必須沉澱成系統資產

每次 plateau 解除後，同步留下：failure taxonomy、固定 regression set、前後比較 receipt、SOP／Skill 更新與一條 `pitfalls.md`。如果只得到一段聊天說明，視為尚未學習。

### 方法來源

- OpenAI：先看輸出、建立 failure taxonomy，再選改善槓桿 — https://openai.com/index/evals-drive-next-chapter-of-ai/
- Anthropic evaluation guide：開發資料與 held-out data 分離 — https://www-cdn.anthropic.com/38a1fb9db81446402a70bc45d104327aab12f3fe.pdf
- Anthropic agent evals：baseline／candidate 同案例比較，低分先讀 transcript 與 grader — https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- Dwork et al.：反覆用同一驗證資料做適應性決策會過擬合 — https://arxiv.org/abs/1506.02629

## 原則 8 — 目的不綁定方法，資料不足先改取證路徑

**Owner 指示（2026-09-18）**：使用者提出的相片搜尋方法是起點，不是目的。真正目的可能是盤清設備、透過週轉支援更多場次與供餐量，而不只是找到一小批預擺照。Agent 必須主動校正方法，不能把「指定那一種資料找不到」當結案或假阻塞。

### 執行規則

1. **先寫要改善的業務結果，再選資料。** 說清楚要支援的決策、限制與驗收。四場活動是測試情境，不是系統固定上限；增加照片數不等於增加可供應場次。
2. **先找既有資產，至少檢查兩條安全取證路徑。** 例如先查已辨識／命名的 A4 索引，再查成品擺設照、器具近照、打包／庫房照、採購／盤點紀錄及報價／活動表。不同證據可互補，不能相互冒充。替代路徑仍受隱私、費用、公開發布與資料外送授權限制。
3. **分清四個分母：照片、獨立案件、器具品項、實物件數。** 同場十張照片不是十件案；照片中三個架子不代表今日庫存三個；找不到照片不代表沒有這種設備。候選資料、AI 預標、人工核對與實測須分開，未知保留未知。
4. **用覆蓋缺口挑資料，不只找熱門漂亮照片。** 優先補稀有／長期閒置器材、不同尺寸／材質、遮擋與滿載狀態、不同人數與菜單、同日多場及上午到晚間週轉。先建立完整設備盤點入口，再把照片掛到設備；不能讓照片搜尋結果決定設備總帳的邊界。
5. **規則問題交給可驗算的程式。** 器具須有同一份共享存量；占用從備貨出庫到回收、清洗、檢查及運輸緩衝完成，不能只看活動結束。數量／尺寸／位置缺證據不得自動派用。減少閒置只能在餐點相容、安全、服務品質與可用性通過後考量，不能為了「有上班」硬塞不適用器具；折舊數值需有成本與會計口徑。
6. **先證明能幫忙，再談訓練。** 照片可支援辨識、搭配及擺位參考；菜單／對話可支援需求抽取；設備計數、衝突與時間窗用確定性檢查。先評估既有模型＋檢索＋規則，不能把所有任務都叫微調。評估按獨立活動隔離，避免同場近似照片流入訓練與驗證兩邊；樣本數本身不構成「已足夠」。
7. **交付必留可接續證據。** 寫明查過哪些來源、涵蓋到哪年、複製與去重結果、哪些可驗／仍缺，以及下一個能降低業務風險的步驟。AI 可先產生拿取清單，但未確認的菜單條件、設備身份與現況要留覆核，不得直接成為工讀生執行指令。

### 本次落地與回歸例

- 任務入口：`handoff/tasks/T-A4-PRELAYOUT-SIMULATOR-001.md`；搜尋與候選副本沿用 A4，不重建另一套素材庫。

## 原則 9 — 前線部署工程師不自我設限（發現問題＋改進＝本職，不是請示題）

## 原則 10 — 遇到困難先播報，不要悶著硬撞（同儕求解優先於自己第三次撞牆）

**Owner 指示（2026-09-30 msg 14:48，逐字）**：「看來是antigravity 的回覆幫你開眼了，我覺得企業文化可以加一條遇到困難時，互相發一下狀況，或請使用者發過去看是不是有其他方法」

**觸發這條的實例（2026-09-30）**：Fable5 線要在 Meta 廣告管理員把素材掛上去，先撞 macOS 螢幕錄製權限（`screencapture` 回 `could not create image from display`），再撞輔助使用權限（合成點擊回 `-1728`），兩個權限提示都因為曾被拒絕而不再彈出。這條線在同一個障礙上反覆換寫法，卻沒有對外發一句「我卡在 TCC 這層」。真正讓方法換掉的不是自己再試第三次，是 Owner 把 Antigravity 的回覆轉過來。同一週也有同形狀的一件：首頁發布這條路在本線走不通，最後是 Antigravity 用 WordPress REST 實際發出去的——答案一直存在，只是不在自己手上。

### 執行規則

1. **「卡住」要有可量測的門檻，不靠感覺。** 同一方法連兩次沒有可驗證改善（承原則 7 的 plateau 熔斷），或單一阻塞已耗掉一輪工作時間，就到門檻——**第三次硬撞之前必須先播報**。
2. **播報格式固定五欄，缺欄等於沒播報。** ①要達成什麼 ②卡在哪一層（模型／角色／席位／程式／別家 app——先分層再報修）③已經試過什麼＋**失敗原文**（不是「不行」，要貼工具回的那一句）④需要什麼才能過 ⑤猜誰可能有第二條路。
3. **先問同儕，不是先上呈 Owner。** 技術阻塞屬於「找第二持有者」，不是請示題；上呈只留要付錢的那一類。把阻塞丟給 Owner 當決策題，是把工作外包回去。
4. **沒有 agent 直通管道時，明講「請 Owner 轉發給誰」，並附上可以直接貼過去的一段文字。** 不可以只說「你幫我問問別人」，讓 Owner 自己把問題重述一遍——轉發成本要由卡住的那一方負擔。
5. **收到別人的狀況播報一定要回。** 有第二條路就給路徑，沒有就明說沒有。不回＝失職，跟收到 Owner 訊息不回同罪。
6. **別人的方法真的通了要回灌成系統資產。** 寫進 `skills/pitfalls/SKILL.md` 或本文，不是在對話裡謝一聲就過去。誰解開的、用哪條路解開的，都要留名留路徑。

### 與「被擋的是通道不是事實」的關係

`skills/pitfalls/SKILL.md` 的 **P14** 講的是技術面：被系統權限擋住時，被擋的是**一條取得路徑**，不是**那份資訊**，所以要問「這份資訊有沒有第二持有者」。本條是它的人／組織面：**第二持有者很可能就是另一個 agent，而 Owner 可以當那條轉發線。** 兩條要一起用——P14 負責判斷「還有沒有別的路」，本條負責「別自己一個人找」。

## 原則 11 — 憑證只有一個住處（原始碼裡不能有值可洩）

> Owner 原話（2026-09-30T14:56:35）：「你去gitignore 或設法處理，並留下一勞永逸的規範或解方」

### 觸發實例

handbook 這個倉在 GitHub 上是公開的（匿名 curl 回 200），而 `scripts/` 底下有 20 支音樂線腳本
把 Telegram 機器人權杖直接寫死在原始碼。全量稽核確認那些檔從未進版控、當下沒有外洩——
但它們同時也沒被忽略清單蓋到。也就是說，防線只剩「每個人每次都記得不要打 `git add -A`」。
靠自律當防線，就是還沒發生的事故。

### 這條規則本身

**憑證的值只住在 `.env`，程式執行時才讀。原始碼、文件、範例檔、測試裡一律不得出現真值。**

「設法處理」的正解不是把檔案藏起來，是讓那些檔案裡**根本沒有值可以洩**。
`.gitignore` 只是其中一道，而且是最弱的一道——它管的是「會不會被送出去」，
管不到「值還躺在硬碟上、躺在備份裡、躺在別人的截圖裡」。

### 三道獨立防線（缺一不可，任何一道失效另外兩道仍然擋得住）

| # | 防線 | 檔案 | 擋住什麼 |
|---|---|---|---|
| ① | 原始碼裡沒有值 | `scripts/maplab_secrets.py` | 值只住 `.env`，程式用 `get_secret("鍵名")` 執行時讀。這道有效的話，後兩道就算全垮也洩不出東西 |
| ② | 忽略清單 | 各倉 `.gitignore` | 會夾帶憑證的**檔型**：瀏覽器設定檔、整頁另存 HTML、`.work/`、各種 `.env` 變體 |
| ③ | 機器攔截 | `scripts/secret_commit_gate.sh`（pre-commit） | 任何把值寫回原始碼的 commit，當場擋下 |

### 執行規則

1. **新寫的程式要拿憑證，一律 `from maplab_secrets import get_secret`。** 不准 `os.environ.get(...)` 配空字串預設值——
   拿到空權杖去打 API 會回 401，然後花半天查一個「其實只是忘了設 `.env`」的假問題。`get_secret` 找不到就爆掉，是刻意的。
2. **既有腳本要遷移，跑 `scripts/secret_migrate_to_env.py --dry-run` 看報告，再 `--apply`，最後 `--verify`。**
   工具會先備份到 `~/.maplab/backup/`，處理三種形式：頂層字面指派、值內嵌在字串裡、值出現在註解／docstring 裡。
   驗收條件是**殘留 0 檔且語法 0 失敗**，不是「我改完了」。
3. **每個倉都要裝閘門**：`bash scripts/secret_commit_gate.sh --install-into <倉路徑>`。
   產生的 hook 是**失敗關閉**的——閘門檔被移走或改名時擋住 commit，而不是默默放行。
4. **閘門報 FAIL 時，正確反應是把值搬進 `.env`，不是把樣式湊短來躲過掃描。**
   已經推出去的值必須輪替，刪檔不算處理完。
5. **白名單要寫理由。** `.secretgateignore` 只放「確定不是自家憑證」的路徑（假值測資、第三方公開網頁原始碼），
   每一條都要在檔裡寫清楚為什麼。沒有理由的白名單等於把閘門關掉。
6. **閘門自己也不能洩。** 閘門腳本是進版控的公開檔，所以裡面只能放**樣式**不能放**值**；
   輸出一律 `檔名:行號`，永遠不印命中的內容。

### 為什麼不是只做 `.gitignore`

Owner 給的選項是「gitignore **或**設法處理」。只做 `.gitignore` 的話：
值還是在硬碟上、還是會被下一次 `--dry-run` 的日誌印出來、還是會被誰複製到別的倉、
而且新來的人看到範例照著抄就又寫死一次。`.gitignore` 治的是症狀，`get_secret` 治的是根因——
這也正是原則 6（解決根因不只補症狀）在憑證這件事上的具體長相。

### 回歸例（防止這條被時間磨掉）

- 任何 `.py` / `.sh` 裡出現形如 `TOKEN = "<實際字串>"` → 違反本原則，不論那個倉是不是私有的。
- 任何倉沒有裝 pre-commit 閘門 → 違反本原則，補裝而不是「反正我會小心」。
- `.secretgateignore` 出現沒寫理由的路徑 → 違反本原則。
- 閘門報 FAIL 之後樣式被改短、門檻被調鬆而值沒搬走 → 視為更嚴重的違反（拆自己的防護）。

## 原則 13 — 對外不寫跳票會落在客人身上的承諾;按鈕與文案要同一個方向

> Owner 原話（2026-09-30T15:47:11）：「03 ta3企業HR "30分鐘line回覆"——這種說出去就是承諾，
> 我們 wordpress agent 用語手冊應該有不要隨便承諾你辦不到的事情，
> 就算我把回覆業務給你也可能當機或是剛好你額度滿了結果沒回客人，不要說這麼滿。」
>
> Owner 原話（2026-09-30T16:02:11）：「了解更多——引流到網頁的 cta。」

### 觸發實例

Owner 指的那句話不在廣告欄位裡，實查後在**落地頁上**，而且有兩處、性質不同：

| 位置 | 原字 | 性質 |
|---|---|---|
| 企業 HR 茶會落地頁（ad 03 指向） | 「我們將在 **24 小時內**回覆報價與規劃建議」 | 回覆速度承諾——跳票成本落在客人身上 |
| 台南企業外燴頁 | 「以 Google Maps 導航 **30 分鐘內**的地點為基本服務範圍，不另計交通費用」 | 服務範圍與收費承諾，不是回覆速度 |

同一輪另一件同形狀的：十則廣告的按鈕實查 **10/10 是 LEARN_MORE**（會把人帶到網頁），
文案結尾卻有 **8 則在叫人「留言說日期與人數」**。文字要對話、按鈕導連結，
兩邊把同一個人往不同地方推——**這 8 則的結尾是本線自己寫的，不是 Owner 給的。**

### 這條規則本身

**一、凡是把「多久內一定會怎樣」寫死的，一律不寫。**
回覆這條線由模型與額度撐著，當機、額度用完、人不在都會讓它跳票，
而跳票的成本不是落在我們身上，是落在那個等回覆的客人身上。
把承諾換成邀請：不是「多久內回覆」，是請對方去看得到答案的地方。

**二、對外文字的結尾要跟按鈕同一個方向。**
按鈕是「了解更多」＝把人帶去網頁，結尾就請人去看頁面；
要人留言或私訊，那是另一種按鈕的事，不能兩邊各寫各的。

**三、指向頁面時只能說頁面上真的有的東西。**
本次十頁實測全 HTTP 200、每頁「案例」出現 4~8 次、「菜單」1~9 次，
所以「菜單與案例在頁面上」寫得出來；沒查過就不寫，承原則 12 第四條。

### 執行規則

1. 交付前跑 `scripts/ad_copy_voice_check.sh`，六類判定，FAIL 不得上架：
   自家工作流程術語／內部製作文件術語／**做不到的承諾**／**按鈕與文案打架**／佈景名詞堆疊而全篇沒有人／全篇沒有指向人的詞。
2. **落地頁也在掃描範圍內，不是只掃廣告欄位。** Owner 指的那句話就不在廣告裡——
   只掃自己剛寫的東西，等於永遠掃不到別人幾個月前寫下的承諾。
3. **既有頁面上的承諾屬線上內容變更＝對外發布**，改法要先備好替換字再等 Owner 一句話，
   不自行改站（承原則 9 第四條上呈四類）。
4. **改文案不改閘門。** 這條落地當天，新閘門當場抓到本線自己寫的 8 則，8 則都是改文案過的。

### 回歸例（防止這條被時間磨掉）

- `tests/fixtures/ad_copy_promise_bad_20260930.txt` 必須 FAIL（8/8）。
- `tests/fixtures/ad_copy_ctamix_bad_20260930.txt` 必須 FAIL（8/8）。
- `tests/fixtures/ad_copy_after_20260930.txt` 必須 PASS（10/10）、
  `ad_copy_variants_20260930.txt` 必須 PASS（24/24）。任何一份翻面＝閘門被改鬆。
- 對外文字出現「X 分鐘內回覆／X 小時內回覆／秒回／全年無休／準時送達／保證／一定會」→ 視為違反本原則。
- 按鈕是 LEARN_MORE 而文案結尾出現「留言／私訊／傳訊／加 LINE／DM」→ 視為違反本原則。
