# Skill: 多日長跑 Harness(Fable 5 收攤前的能力蒸餾)

> 來源:Fable 5 於 2026-07-06~07 實戰(dispatch 修復 → 跨日 PR 看護 → 多線發案)的操作紀律。
> 目的:讓 T1/T2/T3 模型(Opus/Codex/地端)也能規劃並自主執行 3~4 天的任務。
> 核心認知:**多日能力不是長 context,是迴圈**。模型不跨對話記憶、context 會斷;
> 能跑多日靠的是:狀態外存 + 定時自喚醒 + 每次喚醒的標準循環。任何模型照做都能跑。

---

## 1. 開跑前:建立 RUN_PLAN(一次,用最強可用模型)

任何預計超過一個 session 的任務,先寫 `workbook/runs/RUN-<日期>-<代號>/RUN_PLAN.md`:

```markdown
# RUN_PLAN — <任務名>
- 終態定義:完成時世界長什麼樣(可驗證的一句話,例:「PR 全部 merge 且 Telegram 實測回覆正常」)
- 紅線:絕不可做的事(例:不碰真單、不刪原始資料、不直推 main)
- 階段:P1 → P2 → P3(每階段一個可驗證產出,粒度=一次喚醒做得完)
- 驗收方式:每階段怎麼證明完成(指令、預期輸出)
- 喚醒節奏:等外部事件(人/CI/其他 agent)→ 1~3 小時;自己能推進 → 連續做
- 升旗條件:同一步驟失敗 3 次、或需要 Owner 決策 → 停下升旗,不硬幹
```

規劃(P 拆解、驗收設計)是最難的部分,值得用 T0/T1 做;之後每次喚醒的執行 T2/T3 就夠。

## 2. 狀態外存:STATE.md(記憶不在對話裡)

同資料夾維護 `STATE.md`,**每次喚醒結束前必寫**:

```markdown
- 目前階段:P2
- 上次做到:<具體斷點,含檔案/指令/ID>
- 已驗證:<哪些驗收已通過>
- 等待中:<等誰/等什麼事件,預計何時該再查>
- 下次醒來第一步:<一句話,寫給失憶的自己>
```

寫 STATE 的標準=「一個全新 session 的模型,只讀 RUN_PLAN + STATE 就能無縫接手」。
這就是 recall prompt 的任務級版本。

## 3. 自喚醒:讓迴圈跨日活著

依現有基建擇一(優先順序):
1. **Claude Code remote Routines / send_later**:每次結束前排下次喚醒(1~3h),
   喚醒訊息寫死:「讀 workbook/runs/<RUN>/STATE.md,依 RUN_PLAN 繼續;沒變化就靜默重排」。
2. **Mac mini launchd/cron**(比照 patrol-scheduled.sh):定時把同樣的喚醒 prompt 餵給
   `claude -p` 或 Codex CLI。
3. **A1 巡查搭便車**:RUN 資料夾放進巡查掃描範圍,巡查發現 STATE 超過 N 小時未更新 → 升旗。
   (第 3 個是保底,防前兩個都掛)

喚醒節奏原則:等外部事件不要密集輪詢(1h 起跳,深夜拉長到 3~4h);
自己能推進就不要睡。喚醒排程「收攤時必須刪乾淨」——任務完成卻還在喚醒=系統噪音。

## 4. 每次喚醒的標準循環(貼給執行模型的 checklist)

```
1. 讀 RUN_PLAN.md + STATE.md(不要靠記憶,一律重讀)
2. 檢查等待中的事件有沒有發生(PR merge?人回了?檔案出現了?)
   - 沒發生 → 靜默重排下次喚醒,結束(不要向 Owner 報「沒變化」)
3. 發生了/可推進 → 只做「下次醒來第一步」+ 順勢能完成的部分
4. 驗證:跑 RUN_PLAN 寫好的驗收指令,貼實際輸出(不可用「應該沒問題」)
5. 寫回 STATE.md(五個欄位全更新)+ commit push
6. 判斷:終態達成 → 收攤(刪喚醒排程、寫總結、升旗 Owner)
   卡住/需決策 → 升旗 Owner(帶三選一的具體選項,不是開放式問題)
   其他 → 重排喚醒,結束
```

## 5. 崩潰恢復(這套設計的全部意義)

session 斷線、container 回收、模型換代——都不影響任務,因為:
- 一切狀態在 repo(RUN_PLAN + STATE + git 歷史),不在任何對話裡
- 恢復動作永遠一樣:開新 session(任何模型)→ 貼「讀 workbook/runs/<RUN>/ 依 checklist 繼續」
- 這正是 A0 死了 11 天後系統能一天內復活的原因:AGENT_RECALL_PROMPTS 就是這個模式的角色級版本

## 6. 實戰範例(2026-07-06~07,可對照 git log)

dispatch 修復長跑:終態=「系統迴圈恢復+治理落地」;狀態外存=CURRENT_STATUS/發案包/PR;
喚醒=send_later 1h→深夜3h 自適應;每次喚醒查 PR 狀態(git merge-base 判斷,MCP 掛了有備援路徑);
沒變化靜默重排;衝突出現當場 rebase 修掉;全部 merge 後刪排程收攤。
跨了兩個日曆日、十幾次喚醒、數次 MCP 斷線,任務不斷——因為沒有任何關鍵狀態只存在對話裡。

## 7. 給派工者(A0/A1)的一句話規則

> 預計超過半天的任務,一律開 RUN 資料夾再開工;沒有 RUN_PLAN 的多日任務=必然爛尾。
